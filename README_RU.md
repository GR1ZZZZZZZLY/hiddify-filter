# Фильтр подписок HAPP/Hiddify v6.2

v6.2 сохраняет весь функционал v6.1 и добавляет безопасный мост к личному
Telegram-боту: компактный `bot_status.json` и необязательные уведомления только
о значимых изменениях. Старые URL подписок не меняются.

## Что уже делает фильтр

- объединяет `0xRadikal verified` и `Danialsamadi/v2go`;
- использует `fast`, `secure` и `top100` только как рейтинговые сигналы;
- исключает RU по метке источника;
- строго проверяет VLESS, REALITY, TCP/RAW, XTLS Vision, UUID, SNI,
  fingerprint, REALITY public key и опасные TLS-параметры;
- объединяет одинаковые подключения с разными названиями;
- ограничивает концентрацию одинаковых endpoint, IP-сетей, UUID,
  REALITY-ключей и операторских кластеров;
- хранит 96-запусковую обезличенную историю;
- даёт максимальный приоритет узлам, прошедшим локальный GET-тест через Xray;
- не заменяет последнюю успешную публикацию при критической нехватке узлов.

## Публикуемые файлы

- `reality_best.txt` — до 50 лучших текущих строгих REALITY-узлов;
- `reality_stable.txt` — до 100 узлов с присутствием минимум 6 из 8 запусков;
- `reality_durable.txt` — до 50 узлов с присутствием минимум 72 из 96 запусков
  и подтверждением обоими публикующими источниками;
- `reality_local.txt` — до 50 текущих строгих узлов, прошедших минимум 2 из 3
  настоящих GET-проверок через сеть пользователя;
- `reality_tcp.txt` — полный строгий список
  `VLESS + TCP/RAW + REALITY + XTLS Vision`;
- `reality_all.txt` — расширенный безопасный REALITY-список, включая XHTTP,
  SplitHTTP и gRPC;
- `subscription.txt` — нестрогий аварийный резерв всех протоколов без RU;
- `security_report.json` — подробная обезличенная диагностика;
- `bot_status.json` — компактный публичный статус для Telegram-бота;
- `node_history.json` — SHA-256-идентификаторы и счётчики присутствия;
- `checksums.sha256` — контрольные суммы семи подписок.

## Что добавлено в v6.2

- стабильная схема `bot_status.json` версии `1`;
- состояния `healthy`, `degraded` и `failed`;
- счётчики профилей и источников;
- готовность окон STABLE/DURABLE;
- возраст и остаток свежести LOCAL;
- безопасные уведомления о переходах состояния;
- уведомление о сбое workflow с пояснением, что последние хорошие подписки
  сохранены;
- ручной флаг `telegram_test` для одного тестового сообщения;
- защита от сообщений каждые 15 минут при отсутствии значимых изменений.

Telegram-настройка необязательна. Если соответствующих Secrets нет, обе новые
части спокойно пропускают отправку, а подписки обновляются как раньше.

## Контракт bot_status.json

Основные поля:

- `schema_version` — версия контракта, сейчас `1`;
- `filter_version` — версия фильтра, сейчас `6.2`;
- `generated_at_utc` — время последнего успешного пересчёта;
- `health.status` — `healthy`, `degraded` или `failed`;
- `health.reasons` — стабильные машинные коды причин;
- `profiles.*` — путь, количество и состояние каждого профиля;
- `sources.*` — количество конфигураций и роль источника;
- `history.*` — готовность STABLE/DURABLE;
- `local.status` — состояние локального отчёта;
- `local.age_seconds` — возраст локального результата;
- `local.expires_in_seconds` — сколько секунд осталось до трёхчасовой границы;
- `local.selected` — сколько узлов опубликовано в LOCAL;
- `local.current_ok_selected` — сколько выбранных узлов работало в последнем
  локальном тесте.

`healthy` означает, что основные профили и свежий LOCAL доступны. `degraded`
означает, что основные подписки продолжают работать, но LOCAL устарел или
содержит меньше трёх узлов, один из вспомогательных показателей ниже порога либо DURABLE не
сформировался после полного окна. `failed` означает критическую нехватку
основных профилей.

Критический build не публикуется. Поэтому при настоящем сбое файл в
репозитории остаётся последним успешным, а состояние `failed` передаётся
отдельным Telegram-уведомлением. Позже интерактивный бот будет объединять
`bot_status.json` с результатом последнего GitHub Actions run.

`bot_status.json` не содержит URI, IP, UUID, SNI, REALITY-ключи, HMAC-метки,
HMAC-секрет, GitHub-токен или Telegram-токен.

## Telegram-уведомления

Поддерживаются события:

- первое включение мониторинга v6.2;
- переход `healthy ↔ degraded`;
- восстановление после ограничения;
- новый локальный тест и количество выбранных узлов;
- переход LOCAL в `stale` и обратно в `active`;
- первое появление DURABLE;
- ошибка workflow.

Обычный плановый запуск без значимых изменений сообщения не отправляет. Сбой
Telegram API не блокирует обновление подписок. При серии одинаковых сбоев
планировщика отправляется первый сигнал, а последующие подряд ошибки не создают
сообщение каждые 15 минут.

После создания личного бота через `@BotFather` понадобятся два Repository
Secrets:

- `TELEGRAM_BOT_TOKEN` — токен бота;
- `TELEGRAM_CHAT_ID` — числовой ID разрешённого личного чата.

Не помещайте токен в репозиторий, сообщения, скриншоты, URL или команды,
которые сохраняются в истории. Настройку этих Secrets выполняйте только на
следующем этапе вместе с инструкцией для личного бота.

После настройки можно открыть ручной запуск workflow, включить
`telegram_test` и получить одно тестовое сообщение.

## Установка поверх v6.1

1. Распакуйте архив v6.2.
2. В корень репозитория загрузите с заменой:

   - `filter_subscription.py`;
   - `test_filter_subscription.py`;
   - `README_RU.md`.

3. Дополнительно загрузите в корень два новых файла:

   - `telegram_notify.py`;
   - `test_telegram_notify.py`.

4. Отдельно замените `.github/workflows/update.yml` через редактор GitHub.
5. Не удаляйте:

   - `node_history.json`;
   - `local_results.json`;
   - Repository Secret `LOCAL_TEST_HMAC_KEY`.

6. Сделайте коммит в `main`.
7. Откройте
   `Actions → Update filtered HAPP subscriptions → Run workflow`.
8. На первом запуске оставьте `telegram_test` выключенным.
9. После зелёного результата в корне появится `bot_status.json`.

Существующие профили HAPP перенастраивать не нужно. Имена и Raw-URL всех
подписок, включая `reality_local.txt`, сохранены.

## Локальный тестер v1.1.1

Для обновления LOCAL:

1. Полностью отключите HAPP и остальные VPN.
2. Запустите `05-TEST-AND-PUBLISH.cmd`.
3. Дождитесь полного GET-теста, загрузки `local_results.json`, запуска workflow
   и проверки опубликованного результата.
4. Включите HAPP и обновите `REALITY LOCAL 2/3 без RU`.

`05` загружает только `local_results.json`. DPAPI-файл, локальная история,
Xray, временные конфигурации, URI и OAuth-токен не передаются.

Локальные результаты старше трёх часов игнорируются. Отсутствие или
просрочка LOCAL переводит общий статус в `degraded`, но не останавливает
обновление BEST, STABLE, DURABLE и резервных профилей.

## Как читать подробный отчёт

В `security_report.json` особенно полезны:

- `merge.cross_source_identities` — сколько подключений найдено в обоих
  публикующих источниках;
- `history.stable_candidates` — сколько узлов прошло правило 6/8;
- `history.durable_candidates` — сколько прошло правило 72/96 и
  cross-source-проверку;
- `history.window_complete_current` — сколько текущих узлов накопило 96
  наблюдений;
- `outputs.*` — фактическое количество строк в профилях;
- `diversity.*.skipped_*` — сколько кандидатов отброшено лимитами концентрации;
- `local.status` — `active`, `stale`, `secret_missing`, `results_missing` или
  `invalid`;
- `local.qualified_report_nodes` — узлы с результатом не ниже 2/3;
- `local.matched_current_strict` — совпадения с текущим строгим списком;
- `local.selected` — фактический размер `reality_local.txt`.

## Публичность и безопасность

Для обычной Raw-ссылки HAPP репозиторий должен быть публичным. Не помещайте в
него личные или платные ключи.

Upstream-проверка, локальный GET-тест, синтаксическая валидация, история и
совпадение источников не устанавливают личность владельца узла. Публичный
сервер видит ваш IP, время, объём соединений и адреса назначения.

Не используйте публичные узлы для банков, криптокошельков, Госуслуг, рабочих
админ-систем и смены важных паролей. Не принимайте предупреждения браузера о
сертификатах.

История не содержит URI, IP, UUID, SNI или ключи. Исчезнувший URI из истории
восстановить нельзя, поэтому отсутствующий узел никогда не публикуется.
